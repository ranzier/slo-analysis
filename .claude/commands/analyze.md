---
description: 分析某一天的 SLO 异常原因，基于 batch-diffv2 的输出数据生成根因分析报告（含新增聚合维度）
---

用户想了解某个服务在某一天为什么异常数增加了。请按以下步骤操作：

## 1. 从用户输入中提取服务名和日期

从用户输入 "$ARGUMENTS" 中提取：
- **服务名**：如 "open.bangumi.view-gateway"。如果用户没有指定服务名，询问用户。
- **日期**：如 "5月16" 对应目录名 "2026-05-16"（当前年份）。如果用户没有指定日期，询问用户。

## 2. 找到该服务最新的 batch_diffv2 输出目录

在 `output/batch_diffv2/` 下，找到以该服务名为名称的目录（格式为 `{服务名}`）。

例如用户问 "open.bangumi.view-gateway" 服务，则匹配 `output/batch_diffv2/open.bangumi.view-gateway` 目录。

## 3. 读取数据

### 3.1 读取基线日数据

进入 `baseline/` 子目录，对每个接口目录读取：
- `aggregate.json` — 基线日聚合数据

目前，各服务对应的基线日分别是：
1. `open.bangumi.view-gateway`: 5月12日
2. `main.bangumi.season-service`: 5月12日
3. `ogv.player.authunite-service-ogv`: 5月11日

### 3.2 读取异常日数据

在该目录下找到对应日期的子目录（如 `2026-05-16/`）：
- 如果没找到，则告知用户该日期无太大异常，没有相关的异常日志信息可以分析。

如果找到了：

1. 读取 `increased_apis.json` — 获取增量接口列表
2. 对每个接口目录，读取：
   - `target_aggregate.json` — 异常日聚合数据
   - `diff_result.json` — 对比结果（如果存在）
   - `time_windows.json` — 异常时间段（如果存在）
   - `window_*/aggregate.json` — 各异常时间段的详细聚合（如果存在）

注意：基线日聚合数据从 `baseline/{接口目录}/aggregate.json` 读取，不再从异常日目录中读取 `baseline_aggregate.json`。

## 4. 生成分析报告

基于读取的数据，生成一份结构化的根因分析报告，包含以下部分：

### 4.1 异常概览

列出哪些接口错误数增加了，增量和倍率是多少。

### 4.2 下游服务对比

对比基线日和异常日的下游服务失败分布（数据来自聚合表的 `5_下游服务失败` 维度）。

拆分为两张表：

**表1：占比与错误数变化**

┌──────────────────┬──────────────────────┬────────────┬────────────┬────────┬──────────────┬────────────────────┐
│ 下游服务          │ 下游接口              │ 基线日占比  │ 异常日占比  │ 占比变化 │ 异常日错误数  │ 主要错误描述        │
├──────────────────┼──────────────────────┼────────────┼────────────┼────────┼──────────────┼────────────────────┤
│ ...              │ ...                  │ ...        │ ...        │ ...    │ ...          │ ...                │
└──────────────────┴──────────────────────┴────────────┴────────────┴────────┴──────────────┴────────────────────┘

**表2：响应时间与集中度**

┌──────────────────┬────────────┬────────────┬────────────┬────────────┬──────────────┬──────────┐
│ 下游服务          │ 基线avg_ts  │ 异常avg_ts  │ 基线max_ts  │ 异常max_ts  │ 异常日下游IP数 │ 判定      │
├──────────────────┼────────────┼────────────┼────────────┼────────────┼──────────────┼──────────┤
│ ...              │ ...        │ ...        │ ...        │ ...        │ ...          │ ...      │
└──────────────────┴────────────┴────────────┴────────────┴────────────┴──────────────┴──────────┘

填表说明：
- **下游服务 / 下游接口**：来自 `peer_service` 和 `downstream_path`
- **占比变化**：异常日占比 - 基线日占比，正值表示恶化
- **判定**：根据 avg_ts 和 IP 数给出简短判定，如"卡死在deadline"、"快速失败"、"单点故障"、"服务级问题"
- **异常日下游IP数**：`unique_target_ip_count`，少则单点故障，多则服务级问题
- **主要错误描述**：来自 `top_errors` 字段，直接展示错误原文

重点关注：
1. 占比升高的下游服务（新增的问题源）
2. avg_ts 接近 deadline 的下游（超时瓶颈）
3. avg_ts 很低但错误数高的下游（快速返回错误，内部故障）
4. 下游 IP 数少的（单点故障，可针对性处理）

### 4.3 错误类型和描述变化

对比基线日和异常日的错误类型分布（`2_错误类型分布`）、错误描述分布（`3_错误描述分布`），找出新增或占比升高的错误。

### 4.4 可用区和 IP 集中度

对比基线日和异常日的可用区分布（`8_可用区维度`）、下游 IP 分布（`7_实例维度_下游IP`），判断是否存在某个区域或实例集中故障。

### 4.5 超时配置分析

如果有 `11_超时配置维度` 数据，分析：
- 超时配置值（timeout/quota）与实际耗时（avg_ts/p95_ts）的关系
- 是否存在配置不合理（如 timeout 很大但实际耗时卡在某个固定值，说明是下游 deadline 而非本地配置问题）
- 不同超时配置下的错误类型分布

### 4.6 响应体大小分析

如果有 `12_响应体大小维度` 数据，分析：
- 大响应体（10-100KB、100KB+）是否与高耗时相关
- 对比各桶的 avg_ts，判断是否存在大包超时问题

### 4.7 调用方分析

如果有 `13_调用方维度` 数据，分析：
- 错误是否集中在某个特定调用方
- 对比基线日和异常日的调用方分布变化
- 如果某个调用方占比异常升高，可能是该调用方的请求模式变化导致

### 4.8 客户端区域分析

如果有 `15_客户端区域维度` 数据，分析：
- 错误是否集中在某个特定区域
- 是否存在地域性网络问题

### 4.9 请求体大小分析

如果有 `10_请求体大小维度` 数据，分析大请求是否与超时相关（对比各桶的 avg_ts）。

### 4.10 异常时间段分析

如果有 time_windows.json 和 window 子目录数据，分析异常集中在哪些时间段，这些时间段的特征是什么。

对于窗口聚合数据，重点关注：
- 时间桶趋势（`16_时间桶趋势`）中的 top_zone 和 top_peer_service 变化
- 窗口内的下游服务分布与全天是否有差异
- 窗口内的可用区集中度

### 4.11 综合结论

基于以上分析，给出当天异常的最可能的根因（按可能性排序），以及建议的排查方向。

结论应包含：
- 主因、次因的明确判定
- 具体的服务名、IP、时间段
- 是服务级问题还是单点问题
- 是持续性劣化还是突发尖刺
- 建议的排查方向和优先级
- 建议下一步是否需要进一步排查下游某个服务，还是只需要继续排查本服务

## 格式要求

- 所有表格使用 Unicode box-drawing 字符绘制（┌┬┐├┼┤└┴┘│─），不要使用 markdown 表格语法
- 表格示例：
  ┌────────┬────────────┬────────────┬────────┐
  │ 可用区 │ 基线日占比 │ 异常日占比 │  变化  │
  ├────────┼────────────┼────────────┼────────┤
  │ sh001  │ 81.7%      │ 70.0%      │ -11.7% │
  └────────┴────────────┴────────────┴────────┘
- 结论要具体，指出具体的服务名、IP、时间段
- 不要泛泛而谈，要基于数据得出结论
- 如果某个维度数据为空或不存在，跳过该部分分析，不要输出空表格
