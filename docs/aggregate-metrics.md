# 聚合表指标说明文档

## 概述

聚合表（aggregate.json）是 SLO 分析工具对采集到的错误日志进行多维度统计后的结构化输出。每份聚合表包含 11 个维度的分析结果，用于从不同角度定位错误根因。

聚合表在以下场景生成：
- `baseline_aggregate.json` — 基线日（正常日）的日志聚合
- `target_aggregate.json` — 异常日的日志聚合
- `window_N/aggregate.json` — 异常时间窗口内的日志聚合

通过对比基线日和异常日的聚合表，可以发现哪些维度发生了显著变化，从而定位根因。

---

## 维度 1：全局汇总

**输出 key：** `1_全局汇总`

| 字段 | 含义 | 分析作用 |
|------|------|----------|
| total_logs | 采样到的日志总条数 | 反映错误规模 |
| unique_trace_count | 去重后的 trace 数 | 一个 trace 可能产生多条错误日志，该值反映实际受影响的请求数 |
| unique_mid_count | 去重后的用户数 | 反映受影响的用户规模，判断是个别用户还是大面积影响 |
| unique_host_count | 去重后的网关实例数 | 判断是单实例问题还是全局问题 |
| unique_target_ip_count | 去重后的下游 IP 数 | 判断是单点故障还是服务级故障 |
| avg_ts | 平均响应时间（秒） | 判断整体延迟水平 |
| p95_ts | P95 响应时间（秒） | 判断长尾延迟 |
| max_ts | 最大响应时间（秒） | 通常等于 deadline 阈值，确认是否触顶 |

**分析思路：**
- 对比基线日和异常日的 total_logs 判断错误增量
- unique_host_count 接近总实例数说明是全局问题
- avg_ts 接近 max_ts 说明大量请求卡在 deadline 上

## 维度 2：错误类型分布

**输出 key：** `2_错误类型分布`

| 字段 | 含义 |
|------|------|
| error_type | 错误分类名称 |
| count | 该类型的日志条数 |
| pct | 占总日志的百分比 |

**错误分类规则：**
| 分类 | 条件 |
|------|------|
| 超时(DEADLINE_EXCEEDED) | gRPC status_code=4 或 ret=-504 |
| 不可用(UNAVAILABLE) | gRPC status_code=14 或 ret=-503 |
| 内部错误(INTERNAL) | gRPC status_code=13 或 ret=-500 |
| 资源耗尽(RESOURCE_EXHAUSTED) | gRPC status_code=8 |
| 未知错误(UNKNOWN) | gRPC error 包含 "UNKNOWN" |

**分析思路：**
- 100% 超时 → 下游变慢导致
- 出现 -503 → 服务熔断/限流
- 出现 -500 → 下游内部逻辑错误
- 多种错误混合 → 可能是级联故障

---

## 维度 3：错误描述分布

**输出 key：** `3_错误描述分布`

| 字段 | 含义 |
|------|------|
| description | 错误描述原文（来自 status.description） |
| count | 出现次数 |
| pct | 占比 |

取 Top 5。

**分析思路：**
- "处理超时" → 通用超时
- "请求超时" → 客户端侧超时
- 具体错误信息（如 `batchQueryRouteHandle batch query failed`）→ 直接指向代码级 bug
- 对比基线日，新增的错误描述往往是根因线索

---

## 维度 4：入口接口影响

**输出 key：** `4_入口接口影响`

| 字段 | 含义 |
|------|------|
| server_path | 入口 API 路径 |
| count | 错误条数 |
| pct | 占比 |
| downstream_services | 该接口调用的所有下游服务列表 |

取 Top 3。

**分析思路：**
- 确认错误集中在哪个入口接口
- downstream_services 列出了该接口的依赖图，帮助理解调用链

---

## 维度 5：下游服务失败

**输出 key：** `5_下游服务失败`

| 字段 | 含义 |
|------|------|
| peer_service | 下游服务名 |
| downstream_path | 下游接口路径 |
| count | 失败次数 |
| pct | 占总错误的百分比 |
| avg_ts | 该下游的平均响应时间 |
| max_ts | 该下游的最大响应时间 |
| unique_target_ip_count | 涉及的下游 IP 数 |
| top_errors | 该下游返回的 Top 3 错误描述 |

取 Top 5。

**分析思路：**
- **占比最高的下游 = 最可能的根因服务**
- avg_ts 接近 deadline → 该下游是超时瓶颈
- avg_ts 很低但 count 高 → 该下游快速返回错误（内部故障）
- unique_target_ip_count 少 → 单点/少数实例故障
- unique_target_ip_count 多 → 服务级别问题
- 对比基线日占比变化，升高的下游是异常新增的根因

---

## 维度 6：Gateway 实例维度

**输出 key：** `6_实例维度_gateway`

| 字段 | 含义 |
|------|------|
| host_name | 网关 Pod 名称 |
| count | 该实例产生的错误数 |
| pct | 占比 |

取 Top 5。

**分析思路：**
- 各实例占比均匀（3-5%）→ 全局问题，非网关自身故障
- 某实例占比异常高（>15%）→ 该实例可能有问题（内存泄漏、GC 等）
- Pod 名称中的 deployment ID 变化 → 正在滚动发布

---

## 维度 7：下游 IP 维度

**输出 key：** `7_实例维度_下游IP`

| 字段 | 含义 |
|------|------|
| target_ip | 下游实例 IP |
| target_zone | 所在可用区 |
| peer_service | 所属服务 |
| count | 该 IP 的错误数 |
| pct | 占比 |

取 Top 5。

**分析思路：**
- 单个 IP 占比很高 → 该实例故障（可针对性重启/摘流）
- 同一服务的多个 IP 都上榜 → 服务级问题
- 所有 Top IP 集中在同一可用区 → 可用区级别故障
- 对比基线日，新出现的 IP 可能是新扩容的有问题实例

---

## 维度 8：可用区维度

**输出 key：** `8_可用区维度`

| 字段 | 含义 |
|------|------|
| zone | 可用区标识（如 sh001、sh004） |
| count | 该区的错误数 |
| pct | 占比 |

**分析思路：**
- 对比基线日的可用区分布，占比升高的区域是问题区域
- 某区占比从 50% 升到 70% → 该区基础设施可能有问题
- 窗口内可用区占比发生反转 → 可能发生了流量切换/故障转移
- 空字符串的 zone → 网关层直接拒绝，未到达下游

---

## 维度 9：业务数据维度

**输出 key：** `9_业务数据维度`

| 字段 | 含义 |
|------|------|
| param_type | 参数类型（season_id / ep_id / aid） |
| param_value | 参数值 |
| count | 出现次数 |

取 Top 5。

**分析思路：**
- 某个 season_id 占比极高 → 可能是该内容的数据异常导致（如数据量过大、缓存未命中）
- 分布均匀 → 非特定内容触发，是系统级问题
- 对比基线日，新出现的高频 ID 可能是触发 bug 的特定数据

---

## 维度 10：请求体大小维度

**输出 key：** `10_请求体大小维度`

| 字段 | 含义 |
|------|------|
| bucket | 请求数组大小分桶（1-10 / 11-50 / 50+） |
| count | 该桶的错误数 |
| pct | 占比 |
| avg_ts | 该桶的平均响应时间 |

**分析思路：**
- 大请求（50+）的 avg_ts 明显高于小请求 → 大请求导致超时，考虑限制批量大小
- 小请求的 avg_ts 也很高 → 不是请求量问题，是下游本身慢
- 只有小请求出错 → 可能是特定代码路径的问题

---

## 维度 11：时间桶趋势

**输出 key：** `11_时间桶趋势`

| 字段 | 含义 |
|------|------|
| time_bucket | 时间桶起始时间（按 60 秒对齐） |
| count | 该分钟内的错误数 |
| unique_mid_count | 该分钟内的去重用户数 |
| top_zone | 该分钟内占比最高的可用区 |
| top_zone_pct | 该可用区的占比 |
| top_peer_service | 该分钟内占比最高的下游服务 |
| top_peer_pct | 该下游服务的占比 |

取错误数最多的 Top 5 分钟，按时间排序。

**分析思路：**
- 观察 top_zone 在时间线上是否发生切换（如从 sh004 变为 sh001）→ 说明发生了流量切换/故障转移
- top_peer_service 变化 → 不同时间段的瓶颈服务不同
- count 的变化趋势 → 判断是瞬时尖刺还是持续恶化
- unique_mid_count / count 比值 → 接近 1 说明影响面广，远小于 1 说明少数用户重复触发

## 对比表（diff_result.json）

除了单独的聚合表，系统还会生成基线日 vs 异常日的对比结果：

| 字段 | 含义 |
|------|------|
| 全局对比.baseline_logs / target_logs | 两天的日志总量对比 |
| 全局对比.baseline_avg_ts / target_avg_ts | 平均响应时间对比 |
| 下游服务变化[].pct_change | 各下游服务占比的变化量 |
| 可用区变化[].change | 各可用区占比的变化量 |

**分析思路：**
- pct_change 为正 → 该下游在异常日占比升高，是新增的问题源
- pct_change 为负 → 该下游占比下降（可能是其他服务问题更严重，相对稀释了）
